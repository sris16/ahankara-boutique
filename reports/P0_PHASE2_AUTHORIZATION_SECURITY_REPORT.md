## 15. Security Findings Ranked

### CRITICAL FINDING — PRIVILEGE ESCALATION VIA SIGNUP MASS ASSIGNMENT (FIXED)
- **Original Vulnerability**: The `/api/auth/sign-up/email` endpoint, generated by Better Auth, accepted arbitrary `role` and `status` parameters via JSON payload.
- **Attack Vector**: Any unauthenticated client could POST `{"role": "ADMIN"}` alongside standard signup fields.
- **Security Impact**: Complete application compromise. An attacker could trivially provision themselves as an `ADMIN` and gain full access to all protected `/api/admin/*` routes and administrative functions.
- **Root Cause**: Better Auth's `user.additionalFields` automatically maps schema fields to client-writable endpoints unless explicitly constrained.
- **Exact Production Fix**: Added `input: false` to the `role` and `status` configurations in `src/lib/auth.ts`. This native framework constraint explicitly instructs Better Auth to drop these fields from incoming client payloads, preventing mass assignment.
- **Regression Test**: Automated regression test added to `scratch/phase2-security.ts` (`G1`).
- **Before/After Behavior**:
  - *Before*: The hacker account successfully obtained the `ADMIN` role.
  - *After*: The payload injection is safely ignored, and the account defaults to the `CUSTOMER` role.
- **Verification Results**: The regression test cleanly passes. All other authorization tests also continue to pass, proving normal customer signup functionality was preserved.

### ARCHITECTURAL LIMITATION — IN-MEMORY RATE LIMITING
- **Rate-Limiting Root Cause**: Originally, authentication endpoints dynamically provided by Better Auth had no brute-force protections.
- **Implementation**: The custom `checkRateLimit` utility was injected as a wrapper over `toNextJsHandler(auth)` in `src/app/api/auth/[...all]/route.ts`. 
- **Protected Endpoints**: `/auth/sign-in/email`, `/auth/sign-up/email`, `/auth/email-otp/*`, `/auth/forget-password`, `/auth/reset-password`.
- **Configured Limits**: 5 requests per 60-second window.
- **HTTP 429 & Retry-After Behavior**: Supported. Verified returning `HTTP 429` with `Retry-After: 60`.
- **Bypass Prevention**: `src/utils/rate-limit.ts` was patched to strictly use `req.ip` rather than trusting `x-forwarded-for`, closing an IP spoofing bypass.
- **In-Memory Limitation**: The rate limit is currently stored in memory. This is appropriate for single-instance Next.js deployment but will fail to protect a distributed multi-instance deployment (e.g. Serverless). A shared Redis store will be required prior to horizontal scaling.
